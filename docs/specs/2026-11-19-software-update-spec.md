# 软件升级方案规格（2026-11-19）

状态：**代码已实现，未提交；实机演练与首个完整安装包未做**。执行拆分、验证记录与未完成项见 [plan](../plans/2026-11-19-software-update-plan.md)。

## 1. 目标与非目标

目标：

1. 一个升级包可把任意受支持的旧版本直接升到最新版，不需要逐版本依次升级。
2. 单机使用的机器通过界面导入升级包（U 盘）完成升级，不需要命令行或管理员脚本。
3. 组网使用时，客户端发现与服务端版本不一致，可直接从服务端取包升级。
4. 升级失败不丢业务数据，程序可回到升级前的版本。

非目标：

- 不做互联网在线更新，不引入 electron-updater。
- 不通过升级包更换运行时（Electron、JRE、MySQL），这类变更仍发完整安装包。
- 第一期不做「从客户端远程把包上传到服务端」，服务端的包由管理员在该机器本机导入。
- `keysim/` 独立版本，不纳入本方案。

| 现有补丁只替换 `resources/app.asar`，绑定单一旧版哈希，版本号与平台写死在脚本里，靠用户手动执行脚本 | `bw-frontend/scripts/build-kylin-update-patch.cjs`、`build-win7-update-patch.cjs` |

由此得出的三个设计前提：

- 升级包必须按 target 出，不存在跨平台通用包。
- Linux 下不能原地替换安装目录里的文件，除非提权。
- 迁移的记录、补跑、备份已有实现，本方案复用，不另造。

## 3. 不变约束

1. 业务数据目录（`mysql/`、`files/`、`config/`）不被升级过程覆盖或删除。
2. 已发布的迁移脚本只追加，不修改、不删除。
3. 203/204/206 契约、HTTP200 信封约定不变。新增端点属新增契约，按 AGENTS.md 红线 5 在提交正文贴前端调用面。
4. 运行期不新增原生依赖（Win7 ia32、麒麟 ARM64、龙芯均需可用）。
5. 升级包**不签名**（2026-11-20 调整，取代原「以签名为可信边界」的原则）：升级包只由内部人员在内网制作和使用。包内摘要只用于发现损坏，不证明来源；能导入或向服务端放置升级包的人即可让机器运行其中的程序，这一点作为已接受的前提。

## 4. 总体设计

### 4.1 版本目录，而不是原地替换

安装目录保持只读，作为出厂基线。升级内容解到数据目录下的版本目录，由一个指针文件决定当前运行哪个版本：

```text
安装目录/                         # 只读基线，升级不触碰
  resources/app.asar             # 启动引导 + 出厂版本
  bin/integrated/<target>/
    runtime/  database/          # 运行时，升级包不含
    backend/  bootstrap/         # 出厂版本的后端与迁移
    manifest.json

<userData>/system/
  releases/
    current.json                 # 指针：当前版本、上一版本、状态
    <version>/
      app.asar                   # 外壳与前端
      backend/                   # 后端产物
      bootstrap/                 # 种子与全部迁移
      manifest.json
  updates/
    <target>/<style>/<包文件>     # 留存的升级包，供组网分发
  mysql/ files/ config/ logs/ backups/
```

选它的理由：

- Linux 不需要 root，Windows 不需要另起进程去替换被占用的文件，各平台行为一致。
- 切换版本是改一个指针文件，原子完成；回退是把指针改回去。
- 安装目录始终是一份可用的兜底版本。

代价是安装目录里的入口要改成「启动引导」，这是一次性改动，随首个带升级功能的完整安装包发出。

### 4.2 升级包

每个 target 与风格的组合一个文件。内容：

| 内容 | 说明 |
|---|---|
| `manifest.json` | 见下 |
| 清单摘要 | 包头内紧随清单的 sha256，用于发现清单损坏（不是签名） |
| `app.asar` | 完整文件 |
| `backend/` | 完整后端产物 |
| `bootstrap/` | 种子与**从基线起的全部**迁移 |

`manifest.json` 字段：

| 字段 | 含义 |
|---|---|
| `formatVersion` | 包格式版本，当前 `1` |
| `product` | 固定产品标识，防止装错产品 |
| `version` | 目标版本，三段式 |
| `target` | 如 `windows-ia32`、`linux-arm64` |
| `style` | 风格（HJ / HJJ / LJ）。风格在构建时分开，每个风格各出一个包；与本机不一致则拒绝 |
| `runtimeBaseline` | 运行时基线编号，整数 |
| `minFromVersion` | 支持的最低起始版本 |
| `migrations` | 迁移文件名有序列表 |
| `files` | 包内每个文件的 sha256 |
| `sourceCommit` | 构建提交 |

升级包不签名，出包不需要密钥（见 §3 第 5 条）。

### 4.3 版本规则

- 全机只有一个产品版本号，后端、外壳、manifest 取同一个值；构建时不一致则失败。
- 升级包可安装的条件，全部满足才放行：
  1. 清单摘要与 `files` 摘要全部一致；
  2. `product`、`target`、`style` 与本机一致。本机身份只取自安装目录里的出厂程序：target 由运行平台得出，风格读 `app.asar` 内 `public/dist/build-manifest.json` 的 `interfaceStyle`（前端构建时写入）；
  3. `runtimeBaseline` 与出厂程序内 `electron/shared/update-baseline.js` 的 `RUNTIME_BASELINE` 相等；
  4. 本机版本 ≥ `minFromVersion`；
  5. 包版本 > 本机当前版本（禁止用升级通道降级）。
- 第 3、4 条不满足时提示「需使用完整安装包」，并写明原因。
- 更换 Electron、JRE、MySQL 或启动引导本身时，`runtimeBaseline` 加一并发完整安装包。

## 5. 逐项行为与验收

### U01 版本号统一

- 行为：产品版本单一来源；后端运行时可读到该版本。
- 验收：构建出的外壳、后端、manifest 三处版本相同；人为改错一处时构建失败。

### U02 升级包构建

- 行为：一个脚本按 `--target` 和 `--style` 出包，版本取自单一来源，不再写死在脚本里；输出包文件和构建报告（文件名、字节数、sha256、提交）。
- 前端构建把风格写入 `build-manifest.json`；基线放在 `electron/shared/update-baseline.js`。运行组件目录按 target 准备、三种风格共用，所以风格不能记在它的 manifest 里（实现时对原方案的修正）。
- 已发布迁移的清单与最低起始版本记录在 `bw-frontend/build/update-release.json`，每次发布后用 `--record-release` 更新。
- 包内迁移列表必须是上一发布版本迁移列表的超集，且已有文件摘要不变，否则构建失败。
- 验收：对现有每个 target 与风格的组合各出一个包；删掉一个旧迁移或改动其内容时构建失败。

### U03 启动引导与版本选择

- 行为：安装目录入口读取 `current.json`，校验所指版本目录的 manifest 后加载其中的 `app.asar`，并让本机后端与迁移取自同一版本目录；`runtime/`、`database/` 始终取自安装目录。
- 没有 `current.json`、或所指版本校验不通过时，使用安装目录内的出厂版本，并记日志。
- 引导先取得单实例锁再读指针，避免新版本首次启动期间的第二次点击被误判为「上次启动失败」。
- 重装了更高版本的完整安装包后，若出厂版本高于 `current.json` 所指版本，以出厂版本为准并清除指针。
- 验收：无版本目录时行为与现在一致；版本目录文件被改动一个字节时回落到出厂版本且能正常启动。

### U04 导入升级包（单机入口）

- 行为：系统管理页提供「导入升级包」。选择文件后依次执行 §4.3 的检查、解到 `releases/<version>/`、把包留存到 `updates/<target>/<style>/`、写指针为「待确认」、提示重启。
- 导入的包 target 或风格与本机不同时，只校验内容并留存用于分发，不安装，界面明确说明。留存目录相应按 target 与风格区分。
- 任一步失败则不改指针，清理未完成的版本目录，原版本照常可用。
- 验收：正常导入后重启进入新版本；篡改包、错 target、低版本、基线不符四种情况均被拒绝且给出对应原因；解包中途杀进程后重启仍是旧版本。

### U05 启动确认与回退

- 行为：以「待确认」状态启动的新版本，在本机服务就绪且主窗口创建后标记为「已确认」。
- 启动失败且**尚未执行任何新迁移**：自动把指针改回上一版本，下次启动回到旧版，并提示升级未成功。
- 启动失败且**已执行新迁移**：不自动回退。停在错误页，给出日志目录和升级前备份文件路径，由管理员选择「恢复升级前备份并回退」或重试。恢复备份必须是显式操作。
- 只保留当前和上一个版本目录，更早的在确认后清理。
- 已知局限：启动失败的原因无法区分是新版本的问题还是环境问题（例如端口被占用）。未执行迁移时一律回退，需要重新导入升级包。
- 验收：注入后端启动失败（无迁移）后自动回到旧版本；注入迁移后失败时不自动回退、数据库未被改动、备份文件存在。

### U06 跨版本迁移

- 行为：复用现有 `nip_desktop_migrations` 机制，按包内全部迁移补跑缺失项，执行前自动备份。
- 本机数据库中存在包内没有的迁移记录（即库比程序新）时拒绝启动该版本，不执行任何语句。
- 验收：从最低支持版本的数据直接升到最新版，迁移全部补齐、业务数据保留；库比程序新时被拒绝。

### U07 版本信息与取包端点（后端）

- 行为：新增免登录端点 `GET /api/update/info` 与 `GET /api/update/package?target=&style=`，放在 `controller/free/`：
  - 版本信息：返回本机产品版本，以及本机 `updates/` 下各 target 与风格留存包的版本、大小、sha256。走标准 `Response<T>` 信封。
  - 取包：按 target 与风格返回包文件字节流；无对应包时按现有业务码约定返回，不用 HTTP 状态表达。
- 包目录位置由外壳启动后端时传入，后端不自行猜测路径；target 与风格只接受固定枚举值，据此取 `updates/` 内的文件，不接受客户端传路径。
- 免登录的理由：版本检查发生在登录之前；包不含机密。升级包不签名，客户端只核对摘要，服务端上留存的包默认可信（内网、内部人员操作）。
- 验收：未带 token 可取到版本信息；请求不存在的 target 得到业务码拒绝；构造路径穿越的 target 值被拒绝。

### U08 组网时的版本检查（客户端）

- 触发时机：`dataUrl` 指向远端时的每次启动；在网络设置里保存新的服务端地址时。本机模式不检查。
- **版本不一致只提示、不限制使用**（2026-11-20 调整，取代 2026-11-19「禁止进入」的决定）：启动后弹出提示，说明双方版本并给出升级入口；用户可选「继续使用」关闭提示，正常登录和训练。提示在每次启动或页面重载时重新出现。版本不一致时功能是否正常不作保证，提示文案须说明这一点。
- 处理：

  | 比较结果 | 处理 |
  |---|---|
  | 版本一致 | 正常进入 |
  | 服务端更新，且有本机 target 与风格的包 | 提示升级，可继续使用；选择升级则下载、校验 sha256 后走 U04 的同一安装流程 |
  | 服务端更新，但没有对应的包 | 提示需管理员在服务端导入对应平台与风格的包，或用 U 盘升级本机；可继续使用 |
  | 本机更新 | 提示服务端版本较低，建议升级服务端；可继续使用 |
  | 服务端可达但没有版本端点 | 视为服务端是尚无升级功能的旧版本，按「本机更新」处理 |
  | 服务端不可达 | 无法判断版本，按现有的连接失败行为处理，并记日志 |

- 「一致」指产品版本号三段完全相同。不同风格的机器只要版本相同即可组网，版本检查不比较风格（2026-11-19 确认）。
- 机器处于组网模式时升级只切换版本目录，本机数据库不启动、迁移不执行；切回本机模式的那次启动由 U06 补跑。
- 验收：六种情况各有对应提示，版本不一致时关闭提示后可正常登录；提示里能下载或导入升级包；下载中断或摘要不符时不安装；组网模式升级后切回本机模式，迁移补齐且数据保留。

### U09 旧补丁脚本的去留

- 行为：`build-kylin-update-patch.cjs`、`build-win7-update-patch.cjs` 保留到首个带升级功能的完整安装包在现场装完为止，用于维护尚无升级功能的存量机器；之后在单独的提交里移除。
- webgl、serial 等专项补丁脚本不在本方案范围内。

## 6. 发布流程（实施后）

1. 定版本号，全量测试通过。
2. 各 target 构建后端与前端，出升级包。
3. 用上一发布版本和最低支持版本的数据各演练一次升级。
4. 现场：单机用 U 盘导入；组网先在作为服务端的机器导入并重启，其余机器启动时按提示升级。
5. 混合平台的现场，把其他 target 的包也导入服务端用于分发。

需要完整安装包的情况：运行时变更（基线加一）、低于 `minFromVersion` 的机器、尚无升级功能的存量机器。

## 7. 风险

| 风险 | 应对 |
|---|---|
| 首个版本必须人工安装，存量机器无法自动过渡 | 接受；该版本随完整安装包发出，现场装一次 |
| 启动引导有缺陷时无法靠升级包修复 | 引导保持尽量小，逻辑单测覆盖；修复走完整安装包并加基线 |
| 迁移执行后发现新版本不可用 | U05 不自动回退，靠升级前备份显式恢复 |
| 服务端升级时在线客户端被断开 | 导入界面提示需在无人训练时执行；第一期不做在线会话检测 |
| 升级包不签名，来源无法验证 | 接受（2026-11-20）：仅内部人员在内网制作和使用；控制好谁能在服务端导入升级包 |
| 每个操作系统账户各有一份数据目录和版本目录 | 与现状一致（数据库本就按账户分开）；文档中写明 |

## 8. 已确认事项

已确认（2026-11-19）：组网时版本不一致即禁止进入（2026-11-20 改为只提示、不限制使用，见 U08）；风格在构建时分开，每个风格各出一个包（见 §4.2）；不同风格的机器可以互相组网，只要求版本相同（见 U08）。

其余三项（包的容器格式、`app.asar` 内有无原生模块、留存包数量）已在执行计划 §1 给出结论：自定义顺序容器；没有原生模块；每个 target 与风格的组合只留最新一个包。
