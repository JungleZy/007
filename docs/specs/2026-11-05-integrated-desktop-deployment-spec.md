# Electron 整合安装与多平台兼容规格

状态：已实现整合启动、数据库初始化与持久目录，并完成 Windows 独立实例服务链验证；安装包构建与实机验收另述。最新实现和验证见 `docs/guides/integrated-desktop-install.md`，下方“当前仓库事实与差距”表保留实施前基线。

## 用户交付目标

最新补充：用户要求完成资料初始化后交付 **Win7 32 位完整单机安装包**，并授权直接完成适配。已新增独立 Electron22 ia32＋Liberica Java21 x86＋MySQL5.7 Win32 组合，完成真实32位服务链验证。2026-11-06 用户确认 compat2 在此前报错的 Win7 64位机器上正常安装使用；Win7 32位操作系统及外设逐项验收仍未提供。当前实现见 `docs/guides/windows-ia32-install.md`，相同环境后续打包以 `docs/guides/win7-installer-system-dll.md` 的 compat2 流程为准。

- 安装 Electron 应用后即可使用整套系统，不要求客户自行安装数据库、Java、客户端工具或编辑连接配置。
- Windows 原x64构建保留Electron30；Win7兼容交付使用独立ia32组件和compat2安装器，当前已有用户Win7 64位机器的成功反馈。
- 国产 Linux 首期覆盖 x64、ARM64，LoongArch64 后续纳入。Windows ARM64 已由用户明确移出范围；Windows 8/8.1 不作为本轮独立承诺的验收目标。
- 本地完整部署必须能在没有外部数据库/后端的环境中完成首次启动。不能将“Win7 只安装客户端、另连服务器”作为完整单机安装已经满足的证据。
- 多人协同模式共用同一服务端；每台客户端自动建独立数据库不等于协同部署。

## Windows 7 验证安排

Electron 官方已明确：23 及以上不支持 Windows 7/8/8.1，22.x 是最后一个兼容这些系统的主版本。

来源：[Electron Windows 7/8/8.1 deprecation notice](https://www.electronjs.org/blog/windows-7-to-8-1-deprecation-notice)。

上述官方限制保留为背景事实。用户早期选择先保留Electron30，后续明确要求可运行的32位完整单机版，现已单独适配Electron22 ia32、Liberica Java21 x86和MySQL5.7 Win32，不覆盖原x64组合。原NSIS安装器在用户Win7 64位机器发生System.dll崩溃，改用compat2后用户确认安装使用正常。

记录该用户机器的实际反馈，不外推为所有Win7版本/补丁、32位操作系统或外设完整验收。Linux x64/ARM64继续单独验证，LoongArch64后期适配，Windows ARM64不在范围内。

## 安装与目录

安装资源与业务数据分离：

```text
安装目录/
  应用入口
  resources/app.asar
  bin/runtime/<target>/       # 若采用 JVM 后端
  bin/server/<target>/        # 后端产物
  bin/database/<target>/      # 绿色 MySQL 服务端及依赖，只读程序资产
  bin/file/                  # 随包基础资源与工具
  bootstrap/                 # schema、基础种子、迁移与校验清单

应用持久数据目录/
  config/                    # 数据库凭据、网络设置、实例标识
  mysql/                     # 独立 datadir，禁止纳入安装包或更新覆盖
  files/                     # 上传文件与可变资源
  logs/
  backups/
```

- 默认使用操作系统可写的应用数据目录，不假设安装目录可写。数据库实例与使用该实例的 OS 账号/部署方式明确绑定。
- 数据库只监听本机回环地址，按最新要求使用独立端口 6912，并迁移此前默认的 13306 配置。端口冲突应报告，不接管未知实例。
- 应用数据库账号和口令首次初始化时生成并持久保存，后续启动只读取。不能每次启动重新生成导致旧库失联。
- 后端通过受控子进程环境接收 JDBC URL、账号和口令。日志及启动错误不输出凭据。
- 卸载默认保留业务数据；升级不能删除 datadir、上传资源、配置和备份。

## 启动与退出

启动顺序：单实例锁 → 组件/权限/端口预检 → 数据库首次初始化或已有库校验 → 数据库启动及 SQL 就绪检查 → schema/迁移状态检查 → 后端启动与就绪检查 → 文件服务就绪 → 打开业务界面。

- 首次初始化必须有独立临时目录及完成状态；中途失败不得留下看似可用的半初始化库。
- 已有目录非空但状态不明时应停止并报告，禁止通过清空目录来“修复”。
- 初始业务账号、管理员首次登录引导及基础数据由专门 bootstrap 资产定义，不能直接导入开发现场快照。
- 数据库就绪以实际 SQL 连接判断，后端就绪以明确的服务检查判断，不能仅判断进程/端口存在。
- 退出应先等待业务服务结束，再正常关闭数据库；超时需保留可诊断日志，避免将强杀作为默认行为。
- 启动过程中退出、二次启动、数据库异常退出和断电后再次启动都纳入行为定义。
