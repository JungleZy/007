# 软件升级方案执行计划（2026-11-19）

对应规格：`docs/specs/2026-11-19-software-update-spec.md`（U01–U09）。

状态（2026-11-19）：**T01–T10 的代码已实现并留在工作区，未提交；T11 只完成文档与本机冒烟，实机演练未做；T12、T13 未做。** 验证范围与未覆盖项见 §5。每个任务一个提交；任务内的跨栈两侧、修复与其回归测试放同一提交。

## 1. 规格待确认项的结论

| 事项 | 结论 | 依据 |
|---|---|---|
| `app.asar` 内是否有原生模块 | 没有 | 运行期依赖只有 `body-parser`、`compression`、`express`、`formidable`、`nedb-promises`，均为纯 JS；串口实现 `electron/serial/nativeSerialPort.js` 只调用 `child_process`；目录内无 `.node` 文件 |
| 包的容器格式 | 自定义顺序容器，见 T03 | 运行期不新增依赖；Node 内置能力即可流式读写；可在解出任何文件前完成验签 |
| 留存包数量 | 每个 target 与风格的组合只留最新一个 | 导入新包时替换同组合的旧包 |

容器格式说明：文件依次为固定标识、manifest 长度与内容、签名长度与内容、按 manifest 顺序拼接的各文件字节（用内置 zlib 压缩）。不用 zip 是因为 Node 没有内置解压，引入依赖要在 Electron 22 ia32 和龙芯上逐个验证。

## 2. 影响计划的现状

1. **交付组合是 12 个**：Windows x64、Win7 ia32、麒麟 ARM64、龙芯，各 HJ / HJJ / LJ（`docs/guides/desktop-packaging-checklist.md`）。风格由构建环境变量 `NIP_INTERFACE_STYLE` 指定。
2. **保存网络设置只重载页面，不重启程序**（`NetSetting.vue` 保存后 `window.location.reload`；`controller.system.changeConfig` 只写配置）。本机服务只在程序启动时按当时的地址决定是否启动（`electron/index.js:41`）。推论：
   - 启动时是远端、运行中改回本机：本机后端和数据库不会被拉起，需重启程序。
   - 启动时是本机、运行中改成远端：本机后端和数据库继续运行到退出。

   该推论来自读代码，未做运行验证。T10 涉及保存时的版本检查，会一并处理「模式变化时重启」。
3. `electron/index.js` 用 `app.getAppPath()` 定位前端页面。启动引导加载版本目录里的 `app.asar` 后，这个值仍指向安装目录，必须改成相对当前模块定位（T06）。
4. `IntegratedRuntime` 用同一个 `assets` 目录同时取运行时（java、mysqld）和版本内容（后端、迁移、manifest）。版本目录方案要求两者分开（T05）。

## 3. 任务

### T01 可行性验证（不产生提交）

用一次性脚本确认下列各点，结果记到本文件 §5：

- Electron 22 ia32 与 Electron 30 的 `crypto` 都能做 Ed25519 验签。不行则改用 ECDSA P-256，规格 §4.2 同步改一处。
- 主进程能从用户数据目录加载另一份 `app.asar` 的入口，窗口能加载其中的前端页面。
- 用户名含中文时（数据目录路径非 ASCII），Win7 上 `java -jar <版本目录>/backend/quarkus-run.jar` 能启动。现有代码已为 MySQL 的同类问题做了英文路径别名（`windows-runtime-paths.js`），后端可能需要同样处理。
- 龙芯包使用的 Electron 版本下，前两条同样成立。

退出条件：四点都有明确结论；任何一点不成立，先改规格再继续。

### T02 版本号统一（U01）

- 以 `bw-frontend/package.json` 的 `version` 为单一来源。
- 后端构建时取同一个值；增加一个检查脚本，`package.json`、`frontend/package.json`、`backend/pom.xml`、`application.yml` 不一致即失败，并接入现有打包前置步骤。
- 后端提供读取产品版本的单点，供 T09 使用。
- 验证：四处版本一致；改错一处时检查脚本失败。

### T03 升级包读写模块（U02、U04 的基础）

- 新增一个纯 Node 模块，放 `bw-frontend/electron/shared/`，构建脚本与运行期共用：打包、验签、校验 manifest、流式解包到目标目录。
- 解包时拒绝绝对路径和含 `..` 的条目；先写临时目录，全部摘要通过后再改名到位。
- 测试（`electron/test/*.test.cjs`）：往返一致；改一个字节被拒；签名不匹配被拒；路径穿越条目被拒；解包中断不留下目标目录。

### T04 升级包构建脚本（U02）

- 新增 `scripts/build-update-package.cjs --target <t> --style <s>`，从已准备好的运行组件目录和 `app.asar` 取内容，调用 T03 出包并写构建报告。
- `prepare-integrated-runtime.cjs` 的 manifest 增加 `style` 与 `runtimeBaseline`，初始基线为 `1`。
- 迁移只追加的检查：与上一发布版本的迁移清单比对，清单存放位置在本任务内定并入库。
- 签名私钥从仓库外的路径读取，缺失时构建失败并说明；公钥入库。
- 验证：出一个包并用 T03 验签通过；删除或改动旧迁移时构建失败；无私钥时失败且不产出未签名的包。

### T05 运行组件路径拆分（为 U03 做准备，行为不变）

- `IntegratedRuntime` 的入参从一个 `appPath` 拆成「运行时根」（java、mysqld、MySQL 工具，始终在安装目录）和「版本根」（后端、bootstrap、manifest）。本任务里两者仍指向同一目录。
- 验证：现有 `electron/test` 全部通过；隔离实例首次启动、二次启动行为与改动前一致。

### T06 启动引导与版本选择（U03）

- 安装目录入口改为启动引导：读 `releases/current.json`，用 T03 校验所指版本目录，通过则加载其中的入口并把版本根指向它；否则用出厂版本并记日志。
- 出厂版本高于指针所指版本时，以出厂版本为准并清除指针。
- 修正 `app.getAppPath()` 的用法（§2 第 3 点）。
- 公钥与引导代码只存在于安装目录，不从版本目录加载。
- 测试：无指针、指针有效、版本目录被改动、出厂版本更高，四种情况的选择结果。

### T07 导入与安装（U04）

- 主进程新增导入流程：规格 §4.3 的五项检查 → 解到 `releases/<version>/` → 留存包到 `updates/<target>/<style>/`（替换同组合旧包）→ 指针写为「待确认」并记录上一版本 → 提示重启。
- 异 target 或异风格的包只验签并留存。
- 界面：系统管理页增加「导入升级包」入口，显示当前版本、各项检查的失败原因、留存包列表。IPC 两侧同一提交。
- 测试：正常导入；篡改、错 target、错风格、低版本、基线不符各自的拒绝原因；失败后指针未变。

### T08 启动确认、回退与迁移保护（U05、U06）

- 「待确认」版本在本机服务就绪且主窗口创建后标为「已确认」，随后清理更早的版本目录。
- 启动失败且未执行新迁移：指针改回上一版本，提示升级未成功。
- 启动失败且已执行新迁移：不自动回退，错误页给出日志目录和升级前备份路径，提供显式的「恢复备份并回退」。
- 数据库里有当前版本 manifest 之外的迁移记录时，拒绝启动该版本且不执行任何语句。
- 组网模式下没有本机服务可等，以主窗口创建为确认条件。
- 测试：两种失败路径；库比程序新被拒；从最低支持版本的数据直接升到最新（用 `backend/database/` 现有快照搭建）。

### T09 后端版本与取包端点（U07）

- `controller/free/` 下新增两个端点：版本信息（`Response<T>` 信封）、按 target 与风格取包（字节流）。包目录由外壳通过环境变量传入；未传入时版本信息照常返回、留存包列表为空。
- target 与风格只接受固定枚举，不拼接客户端传入的路径。
- 外壳启动后端时传入包目录（`integrated-runtime.js` 的后端环境变量处）。
- 测试（REST Assured）：不带 token 可取版本信息；不存在的组合得到业务码拒绝；非枚举值被拒；取到的字节与文件一致。
- 提交正文按红线 5 贴前端调用面的 grep 结果（新增端点，现有调用面应为空）。

### T10 组网版本检查与阻断（U08）

- 主进程在两个时机检查：`dataUrl` 为远端的启动；保存网络设置。
- 按规格 U08 的六种情况处理。阻断页保留「网络设置」和「导入升级包」两个出口；有对应包时提供「下载并升级」，下载后校验 sha256 再走 T07 的同一流程。
- 保存网络设置后若本机/远端模式发生变化，重启程序而不是只重载页面（§2 第 2 点），保证本机服务的启停与设置一致。
- 测试：用假服务端覆盖六种情况；下载中断与摘要不符不安装。
- 手动验证：两台机器，一新一旧，双向各试一次。

### 5.3 真实主进程冒烟（无头 Electron 30 + 假服务端，未留在套件内）

出厂程序为临时目录中的 3.1.3，服务端声明 3.1.4 并提供 3.1.4 升级包（含生产依赖的真实 `app.asar`，约 60 MB）：

1. 启动 → 检查结论为「服务端更新、有可用包」并阻断 → 下载、验签、安装 → 指针为待确认。
2. 重启 → 应用入口来自 `releases/3.1.4/app.asar` → 指针变为已确认 → 检查结论为「一致」。
3. 把已确认版本的 `app.asar` 追加一个字节 → 引导校验失败并记日志 → 出现「程序文件损坏」对话框。
4. 服务端降为 3.1.2 → 结论为「服务端较低」并阻断；服务端不可达 → 不阻断。
5. 新版本入口加载失败（故意缺依赖）→ 自动回退并记录失败原因。
6. 开发态（非整合）启动 → 升级功能不可用、不阻断。

### 5.5 实现与原计划的差异

- 本机风格与基线取自出厂 `app.asar`，不写入运行组件 manifest（运行组件三种风格共用）。
- 入口拆成 `main.js`（引导）+ `electron/app-main.js`（原入口）。**存量的 webgl 专项补丁脚本只向旧包拷入 `main.js` 与 `graphics.js`，按当前源码再跑会产出缺少 `electron/bootstrap` 的坏包**；这些脚本针对的是已交付的旧版本，不应再对新源码使用。
- 后端 `pom.xml` 版本由 3.1.1 改为 3.1.3，`application.yml` 的 `version` 改为引用构建版本。
- 签名密钥对已生成：私钥在 `~/.config/nip-update-signing/ed25519-private.pem`（仓库外），公钥已写入 `electron/shared/update-keys.js`。**T12 之前可以随时重新生成；一旦随完整安装包发出，更换公钥就需要再发完整安装包。**
